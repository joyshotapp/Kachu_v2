# Kachu+ Meta 自助授權流程設計
## 針對 SMB 商家的完整可行流程 v1 設計稿

版本：v0.2  
更新日期：2026-05-09  
文件性質：產品／流程設計稿（非既有功能說明）

---

## 這份文件在做什麼

這份文件只處理一個問題：

- 商家若想把 Facebook / Instagram 連到 Kachu+，應該走什麼流程
- 這個流程對 SMB 商家會不會太複雜
- 目前程式已做到哪裡，還缺哪一段
- 若要開發第一版，完整可行流程 v1 要做到什麼

這份文件刻意把「現況」與「提案」分開，避免把尚未實作的內容誤寫成既有功能。

---

## 一、已查證的現況

### 1. 已存在的能力

- 系統已經有 Meta API client，可對 Facebook / Instagram 執行發文與查詢 insights。
- 系統已經有 connector account 儲存機制，可把 Meta 憑證寫入資料庫。
- 系統已經有使用已保存 Meta 憑證來執行貼文發布與成效查詢的流程。

### 2. 尚未存在的能力

- 沒有 Meta OAuth 起始入口。
- 沒有 Meta OAuth callback endpoint。
- 沒有讓商家自己選擇 Facebook Page 的頁面。
- 沒有在 LINE 對話中觸發「連接 FB/IG」後自動引導授權的流程。
- 沒有商家自助完成授權後的成功通知流程。

### 3. 目前實際上怎麼連接 Meta

目前是由工程端或內部工具直接呼叫後端 API，把以下資料寫入 connector account：

- access_token
- fb_page_id
- ig_user_id
- fb_access_token

也就是說，現在已有的是「連好之後可以用」，缺的是「商家自己把帳號連進來」。

---

## 二、設計目標

對 Kachu+ 的目標客群來說，Meta 連接流程必須符合以下原則：

1. 商家不需要理解 access token、page id、ig user id。
2. 商家不需要進工程後台，也不需要把技術值交給 BD/CS 手動轉貼。
3. 流程應該在 3 到 4 個明確步驟內完成。
4. 若 Facebook 可連但 Instagram 尚未正確綁定，流程仍可部分成功，不應整包失敗。
5. 商家完成後，要能立即知道「已連好什麼、還差什麼、下一步能做什麼」。

---

## 三、產品決策（已定案）

以下規則視為完整可行流程 v1 的固定前提：

1. 一個 tenant 只允許綁定一個 Facebook Page。
2. 若 Instagram 尚未綁定，允許 Facebook 單獨成功。
3. 重新授權與解除綁定，同時提供 LINE 入口與網頁入口。
4. 第一版不做臨時頁面湊合，而是直接做較完整的前端體驗。

---

## 四、已定案的完整可行流程 v1

### 流程總覽

1. 商家在 LINE 說：「我要連接 FB」或「我要連接 FB/IG」
2. 系統先檢查該 tenant 是否已有既有 Meta 連接
3. Kachu+ 在 LINE 回一個按鈕，請商家點擊授權連結
4. 商家在瀏覽器登入 Meta 並授權
5. 系統取得商家可管理的 Facebook Pages
6. 商家選擇要綁定的 Facebook 粉專
7. 系統檢查該粉專是否已綁 Instagram 商業帳號、授權是否足夠、是否需要覆蓋舊連接
8. 系統保存 connector
9. 系統在網頁與 LINE 同步通知結果
10. 商家後續可從 LINE 或網頁重新授權、解除綁定、查看目前連接狀態

### 為什麼不建議把授權完整做在 LINE 裡

- OAuth 本身需要跳轉與登入，瀏覽器承載比 LINE 對話穩定。
- Page 選擇與錯誤說明若塞在聊天訊息內，對 SMB 商家更混亂。
- LINE 最適合扮演「入口與結果通知」，不適合扮演完整授權 UI。

## 五、商家實際會經歷的流程

### Step 1：在 LINE 發起

商家說：

> 我要連接 FB/IG

Kachu+ 回覆：

> 好，接下來我會帶你完成 Facebook / Instagram 連接。  
> 你只需要登入 Meta，選擇要連接的粉專即可。  
> 完成後我會回來告訴你結果。

按鈕文案建議：

- 立即連接 Facebook

若系統發現此 tenant 已有既有連接，LINE 不應直接覆蓋，而是要先說明目前狀態，例如：

> 你目前已經連接 Facebook 粉專「四時循養堂」。  
> 如果你想重新授權或改綁別的粉專，可以繼續下一步。

### Step 2：開啟授權頁

頁面標題建議：

- 連接 Facebook 與 Instagram

頁面文字建議只講三件事：

- 你即將授權 Kachu+ 存取你的 Facebook 粉專資料
- 若你的粉專已連結 Instagram 商業帳號，系統也會一起完成 IG 連接
- 整個流程大約 1 分鐘

CTA 文案：

- 使用 Facebook 繼續

### Step 3：Meta OAuth

Meta 登入與授權完成後，系統進 callback。

此時後端要做三件事：

- 交換 access token
- 取得使用者可管理的 Facebook Pages
- 建立此次授權流程的暫存狀態，供後續粉專選擇與覆蓋確認使用

### Step 4：選擇粉專

若只有一個 Page：

- 自動略過選擇步驟，直接往下處理

若有多個 Page：

- 顯示簡單列表，請商家選一個要連接的粉專

這一頁只能做一件事：

- 選擇要連接哪一個 Facebook 粉專

不要在同一頁加入太多設定，例如：

- 是否同步貼文
- 是否同步留言
- 是否開啟洞察報表

第一版先不要做，避免選項爆炸。

若系統判斷：

- 該 tenant 目前已綁另一個 Facebook Page

則這一步需要額外出現「覆蓋既有連接」確認，但仍維持單一決策，不擴散成多設定頁。

### Step 5：自動檢查 IG

商家選定 Page 後，後端自動檢查：

- 該 Facebook Page 是否已連接 Instagram business account
- 本次授權是否具備該粉專所需權限
- 該 tenant 是否已有既有連接需要被覆蓋

結果有兩種：

1. 已連接 IG
   Facebook 與 Instagram 一起綁定成功。

2. 未連接 IG
   Facebook 先完成，Instagram 標記為尚未連接。

這是第一版最重要的 UX 原則之一：

- FB 成功不應因 IG 缺失而整體失敗。

若權限不足：

- 不進入成功頁，改進入失敗／補救頁，明確告知目前登入帳號沒有足夠粉專管理權限。

### Step 6：完成通知

網頁成功頁建議分成兩種文案。

#### 情況 A：FB + IG 都完成

> 已成功連接 Facebook 粉專「四時循養堂」與 Instagram 帳號。  
> 你現在可以請 Kachu+ 幫你處理社群貼文與成效整理。

#### 情況 B：只有 FB 完成

> 已成功連接 Facebook 粉專「四時循養堂」。  
> 目前尚未偵測到對應的 Instagram 商業帳號，因此 IG 功能尚未開通。  
> 若之後完成綁定，可再重新連接一次。

同時 LINE 要補一則通知：

- 已完成 Facebook 連接
- Instagram 是否已連接
- 下一句建議指令是什麼

### Step 7：後續管理

完整可行流程 v1 不只支援第一次接通，也要支援後續管理。

商家應可透過兩條入口進行：

1. LINE 入口
   - 我要重新授權 FB/IG
   - 我要解除 Meta 連接
   - 我現在連的是哪個粉專

2. 網頁入口
   - 重新授權
   - 解除綁定
   - 查看目前 Facebook / Instagram 連接狀態

## 六、LINE 對話稿建議

### 1. 商家主動發起

商家：

> 我要連接 FB/IG

Kachu+：

> 可以，我現在帶你完成 Facebook / Instagram 連接。  
> 你只要點下面按鈕登入並選擇粉專即可。  
> 完成後我會直接在這裡告訴你結果。

按鈕：

- 立即開始連接

### 2. 完成後回推

#### 全成功版本

> 已幫你完成 Facebook 與 Instagram 連接。  
> 你現在可以直接說：  
> 「幫我寫一篇 FB 貼文」  
> 或  
> 「幫我看一下最近的 Meta 成效」

#### 部分成功版本

> Facebook 已連接完成。  
> 但目前還沒有偵測到 Instagram 商業帳號，所以 IG 功能暫時還不能用。  
> 如果你之後把 IG 連到這個粉專，可以再跟我說一次「我要連接 FB/IG」。

### 3. 失敗時回推

> 這次 Facebook 連接沒有完成。  
> 常見原因是授權中斷，或目前登入的帳號沒有該粉專管理權限。  
> 你可以重新點一次連接，若還是不行我再協助你排查。

### 4. 重新授權

商家：

> 我要重新授權 FB/IG

Kachu+：

> 可以，我會帶你重新完成 Facebook / Instagram 授權。  
> 若你目前已綁定舊粉專，完成後會以新設定覆蓋。

### 5. 解除綁定

商家：

> 我要解除 Meta 連接

Kachu+：

> 可以，我先帶你確認解除綁定。  
> 完成後，Kachu+ 就不會再使用目前的 Facebook / Instagram 連接。

## 七、頁面設計建議

第一版直接做較完整前端，不做一次性臨時頁。最少需要 5 類頁面狀態。

### 頁面 A：授權起始頁

目的：

- 降低商家對授權的疑慮
- 明確說明這次會做什麼

頁面內容：

- 標題
- 三行說明
- 一個主要按鈕

### 頁面 B：粉專選擇頁

目的：

- 在多個 Page 的情境下，讓商家做唯一一次選擇

頁面內容：

- 目前可連接的 Facebook 粉專列表
- 每列只顯示 Page 名稱與選擇按鈕
- 若已有既有連接，清楚顯示目前已綁定的 Page

### 頁面 C：覆蓋確認頁

目的：

- 當 tenant 已有既有 Facebook Page 連接時，讓商家明確確認是否覆蓋

頁面內容：

- 目前已綁 Page
- 新選 Page
- 覆蓋確認按鈕
- 返回重選按鈕

### 頁面 D：完成結果頁

目的：

- 清楚說明成功範圍
- 告訴商家下一步怎麼用

頁面內容：

- 已連接項目
- 未連接項目
- 下一步推薦指令

### 頁面 E：失敗／補救頁

目的：

- 在權限不足、授權中斷、沒有可用粉專等情況下，提供清楚補救方向

頁面內容：

- 發生了什麼
- 最常見原因
- 重新嘗試按鈕
- 返回 LINE 提示

## 八、對 SMB 來說是否過於複雜

### 若做成目前後台填值方式

答案是：非常複雜，而且不適合作為產品化流程。

原因：

- 商家不會知道 access token 是什麼
- 商家不會知道 fb_page_id / ig_user_id 從哪裡拿
- BD/CS 也不應扮演 token 搬運工

### 若做成本文建議流程

答案是：可接受。

前提是整體體驗被壓縮成：

1. 在 LINE 點一下
2. 登入 Meta
3. 選一個粉專
4. 完成

對 SMB 商家真正困難的地方，不是 OAuth 本身，而是以下兩件事：

- 他登入的 Facebook 帳號是否真的有粉專管理權限
- 他的 IG 商業帳號是否已經正確連到該 Facebook Page

所以設計時要讓系統能把這兩類問題講得非常白話，而不是丟技術名詞。

需要新增：

- 授權起始頁
- 粉專選擇頁

### LINE 對話

需要新增：

- 「連接 FB/IG」語句辨識
- 回傳授權連結
- 完成後推播結果通知
- 「重新授權 FB/IG」語句辨識

## 十、第一版不建議一起做的東西

以下容易讓範圍膨脹，第一版應先排除：

- 在授權流程中同時設定貼文同步偏好
- 在授權流程中同時設定留言管理規則
- 在授權流程中要求商家理解不同 token 類型
- 在授權流程中要求商家手動輸入任何 ID

完整可行流程 v1 的成功標準是：

- 商家能靠自己完成 Facebook 連接，且若 IG 已正確綁定就一併完成。
- 若已有既有連接，商家可自行完成覆蓋或重新授權。
- 若要解除 Meta 連接，商家可自行從 LINE 或網頁完成。

## 十一、建議的驗收標準

### 功能驗收

- 商家可從 LINE 取得授權入口
- 商家可完成 Meta 登入與授權
- 商家可選擇一個 Facebook 粉專進行綁定
- 系統可保存 Facebook connector
- 若該粉專有 IG 商業帳號，系統可自動保存 ig_user_id
- 完成後 LINE 能收到結果通知
- 若已有既有連接，系統可要求商家確認是否覆蓋
- 商家可從 LINE 與網頁重新授權
- 商家可從 LINE 與網頁解除綁定
- 商家可查看目前已綁定的 Facebook Page 狀態

### UX 驗收

- 商家在流程中不會看到 token、page id、ig user id 等技術詞
- 失敗訊息能用白話說明下一步
- FB 成功、IG 未完成時，商家仍可理解目前可用範圍
- 已有既有連接時，商家能理解自己是否正在覆蓋舊設定
- 重新授權與解除綁定不需要工程介入

## 十二、結論

Kachu+ 目前不是沒有 Meta 能力，而是少了「商家自助授權」這一段產品化流程。

若維持目前做法，Meta 串接高度依賴工程介入，不適合作為 SMB 產品流程。

本文已不再以最小可行流程為目標，而是直接採用完整可行流程 v1。

在這個版本下，商家的核心連接路徑仍維持簡單：

- LINE 發起
- 瀏覽器登入 Meta
- 選擇粉專
- 返回 LINE 看結果

但完整可行流程 v1 會額外把以下能力一起產品化：

- 舊連接覆蓋確認
- Facebook 單獨成功、Instagram 延後補齊
- 重新授權
- 解除綁定
- 連接狀態可查詢

這樣的設計對 SMB 仍屬可接受複雜度，同時避免第一個真實商家上線後又回到工程手動補洞。
