# Kachu Google Business 接入頁規格

更新日期：2026-05-05

## 目的

這份文件定義 Kachu 為 Google Business Profile API 接入所需的商家正式頁面最低規格。

背景事實：

- Google Business Profile API 准入申請流程將 `Company website` 列為必填欄位。
- 目前實際送件已開立 support case `8-4117000041079`，審核結果仍待回覆。
- Google 官方文件目前可直接確認的是：API access 審核發生在 Google Cloud project 層級，申請者必須管理一個已驗證且啟用超過 60 天的 Google 商家檔案，並擁有代表該商家的網站。
- 因此，網站要求應先視為 applicant 或 project 層級的准入門檻，而不是已被官方白紙黑字證明為每個 downstream tenant 都必須各自具備獨立網站的硬規則。

這份規格的目標不是替每個客戶做完整官網，而是建立一個足以支撐 Google API 接入、同時可累積 Kachu SEO 權重的標準化商家頁。

## 產品決策

Kachu 對沒有既有官網的商家，採用以下預設策略：

- 使用共用主網域。
- 每個商家使用獨立子網域。
- 形式為 `<tenant-or-brand>.kachu.tw`。
- 所有商家頁由同一套平台與 hosting 管理，不為單一 tenant 個別購買網域或主機。

採用子網域而不是路徑的原因：

- 商家對外識別更清楚。
- 後續若要接 Search Console、站點驗證、structured data 或獨立 landing page 管理，子網域邊界較乾淨。
- 仍可把整體內容資產集中在 Kachu 體系內，累積品牌與搜尋權重。

## 適用範圍

此規格適用於以下情境：

- Kachu 準備申請或維持 Google Business Profile API access。
- Kachu 需要準備 applicant 級別的正式網站資產，以降低 Google 審核風險。
- Kachu 要為沒有既有正式官網的商家建立標準化商家頁，作為 onboarding 與對外識別資產。
- Kachu 要由系統保存 tenant 對應的正式網址，供後續 GBP、SEO、品牌頁與其他 connector 共用。

## 官方已確認與未確認事項

### 官方已確認

- Google Business Profile API access 是 Google Cloud project 層級核准。
- 申請者必須管理一個已驗證且啟用超過 60 天的 GBP。
- 申請者必須擁有代表該商家的網站。
- 第三方合作夥伴可在專案核准後，透過 OAuth 或 manager access 代表客戶管理商家資訊。

### 目前未有官方明文保證

- 每個 downstream tenant 是否都必須各自具備獨立網站，Google 文件沒有直接這樣寫。
- 共用主網域加子網域頁面是否一定會被 Google 接受，Google 文件沒有直接保證。

因此，Kachu 的產品策略應理解為：

- 「Kachu 平台至少需要一個可通過 applicant 審核的正式網站資產」是高可信的要求。
- 「為每個 tenant 提供正式頁面」是降低審核、營運與品牌一致性風險的產品策略，不是目前已被官方逐字寫死的規定。

## 必備內容

以下內容應視為 Kachu 商家正式頁的最低建議規格。若 Kachu 要把某個 tenant 的頁面當成對外正式資產或審核輔助材料，至少應達到以下水準。

### 1. 商家識別資料

- 商家名稱。
- 商家名稱英文或替代名稱（若有）。
- 商家主分類或業種。
- 商家一句話描述。

要求：

- 商家名稱必須和 Google Business Profile 上的名稱一致，或至少是可合理對照的正式名稱。
- 不得使用 Kachu 內部代號或暫用名稱代替正式商家名。

### 2. 聯絡與實體資訊

- 電話。
- 完整地址。
- 營業時間。
- 聯絡方式補充資訊，例如 LINE、Facebook、預約方式。

要求：

- 地址、電話、營業時間應與 Google Business Profile 內容一致。
- 若商家是到府、無固定門市或服務區型態，頁面上也必須明確寫出服務區與聯絡方式。

### 3. 服務內容

- 主要服務項目或產品項目。
- 每項服務的簡短說明。
- 適用對象或常見情境。

要求：

- 內容要能讓 Google 或使用者理解這家商家實際提供什麼服務。
- 不可只放一句過於空泛的品牌標語。

### 4. 商家介紹

- 商家簡介。
- 經營者、品牌故事或專業背景摘要。
- 商家主張或特色。

要求：

- 介紹內容需能證明這是實際營運中的商家，而不是只為送審臨時建立的空殼頁。

### 5. 視覺與信任訊號

- 商家招牌照、門面照、服務照或代表圖至少一張。
- 若有 logo，應放置正式 logo。

要求：

- 圖片不需豪華，但應與商家真實身份一致。
- 不可使用和商家無關的素材圖當唯一主圖。

### 6. 法規與頁尾基本資訊

- 頁尾商家名稱。
- 頁尾聯絡資訊。
- 隱私權說明或最基本的聯絡責任說明。

要求：

- 若頁面含聯絡表單、追蹤碼或任何資料收集，應補上隱私權說明頁或對應區塊。

## 必須與 Google Business Profile 一致的欄位

以下欄位不應容忍明顯不一致，否則會提高 Google 審核、信任與後續營運風險：

- 商家名稱。
- 電話。
- 地址或服務區。
- 營業時間。
- 商家分類。
- 官方網站 URL。

若 tenant 已有 GBP，Kachu 在 onboarding 中應把這些欄位視為對帳欄位，而不是單純展示欄位。

## 建議但非硬性必備內容

以下內容不是最小接入門檻，但建議預設提供：

- Google 地圖嵌入。
- 常見問題。
- 顧客評論摘錄。
- 預約或聯絡 CTA。
- Facebook、Instagram、LINE 官方帳號連結。
- 結構化資料，例如 `LocalBusiness` schema。
- SEO meta title、meta description、OG image。

## 子網域與網址規則

Kachu 應採用以下原則：

- 每個商家固定一個子網域，例如 `goodbone.kachu.tw`。
- 子網域 slug 應穩定，不要頻繁變更。
- 一旦作為 Google `Company website` 提交，就不應隨意更換網址。
- 頁面必須全站 HTTPS。
- 頁面必須可公開存取，不可要求登入。
- 頁面必須可被搜尋引擎索引，除非 Google 審核策略有明確例外。

slug 建議來源：

- 先用品牌英文名或拼音。
- 若名稱重複，附加地區或短代碼。
- 不使用隨機 UUID 當對外網址。

## 頁面品質底線

即便是陽春版商家頁，也不應低於以下底線：

- 不是空白頁或僅有一句介紹。
- 沒有 `Lorem ipsum`、樣板假文或待補 placeholder。
- 沒有明顯與商家不符的預設圖片或測試資料。
- 行動版可正常閱讀。
- 首屏就能看到商家名稱與主要聯絡資訊。
- 頁面載入正常，不是半成品或 broken layout。

## Kachu 內部作業流程建議

若 Kachu 要把 tenant 商家頁納入正式接入資產，建議先完成以下流程：

1. 收集商家基本資料。
2. 對齊商家名稱、電話、地址、營業時間與 GBP 資料。
3. 生成對應子網域商家頁。
4. 由內部完成一次人工校對，確認沒有 placeholder 與不一致資料。
5. 若該 tenant 為正式串接目標，再進入 `/auth/google/connect?tenant_id=<tenant>&platforms=gbp`。
6. 如需在 Google API access、support case 或後續審查中提供對應網址，再提交該子網域網址。

## 上線阻擋條件

若出現以下任一情況，Kachu 不應承諾該商家可立即完成 Google Business API 串接：

- Kachu 專案本身尚未取得 Google Business Profile API access。
- Kachu 沒有可提交的 applicant 級別正式網站資產。
- 商家頁資訊與 GBP 明顯不一致。
- 商家連正式名稱、電話、地址都尚未確認。
- 頁面仍是測試站、暫存站或不可公開存取網址。

## 最低驗收清單

只有在以下條件全部成立時，才應視為「可作為正式頁資產使用」：

- 子網域已建立。
- HTTPS 正常。
- 商家名稱、地址、電話、營業時間已填完。
- 至少一段商家介紹與一組服務說明已填完。
- 至少一張真實商家圖片已上線。
- 頁面無 placeholder。
- 頁面資訊已和預計綁定的 GBP 資料核對，或至少已與 tenant 主資料核對。

## 後續實作方向

這份文件對應的產品實作方向應為：

- 由 Kachu 後台或 onboarding 流程直接生成商家頁。
- 子網域、SEO metadata 與基本 schema 採模板化。
- 把商家頁建立視為 Kachu 的標準品牌資產與 onboarding 配套，而不是送審前的臨時補救。

結論：

對 Kachu 而言，這不是「是否要替每個客戶客製完整網站」的問題，而是「是否要內建一個可規模化、可驗證、能支撐 Google 審核與後續 onboarding 的正式頁資產」。現階段答案仍然是要，而且預設採共用主網域加獨立子網域；但它更像是平台級固定資產與風險緩解手段，而不是已被官方證實為每個 tenant 都必須各自重新過審的一次性成本。
